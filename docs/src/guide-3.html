Part VII · Plumbline, the system

Chapter 28The thesis and the architecture

A plumb line does not measure a wall. It gives you a reference that is true, so the wall's deviation from it becomes visible and measurable. That is the whole design idea: establish what the agent's nominal behaviour is, then measure departure from it under conditions that should not cause any.

The tool asks you to declare what must always be true of a run, then attacks those claims with meaning-preserving input changes, and reports which claim broke, under which change, at which named step, how often, and with what confidence interval. The output is a bug report with statistics attached, not a score.

src/plumbline/
  core/       trajectory model, typed argument comparison, sequence alignment
  spec/       the invariant DSL
  adapters/   Claude client: trial-keyed cache, budget accounting
  perturb/    the perturbation library and the equivalence guard
  runtime/    parallel runner, response cache, cumulative spend cap
  analysis/   conformance, consistency, equivalence, Wilson, permutation tests
  report/     the certificate and the HTML report
agents/ap/    the system under test: sqlite tools, policy, three architectures
experiments/  the study

The layering matters. core knows nothing about accounts payable. agents/ap is a specimen, not the product. You could point the instrument at a different agent by supplying a different policy specification and adapter.

Chapter 29Trajectories in code

A Step records one observable event: kind, name, arguments, output, error, latency, token counts. A Trajectory is an ordered list of steps plus metadata: which arm produced it, which task, which perturbation, which exact variant, which model.

Two design decisions are load-bearing.

A failed call did not happen

If a tool raises, the step is recorded but does not count as the control having run. This sounds obvious and was originally wrong, and the bug is instructive enough that Chapter 40 covers it in full. An agent that invoked the vendor check with a bad argument, got an error, and moved on has not run the vendor check. A harness that counts it as run certifies a control that never executed, which is worse than no harness.

Deliberation is not behaviour

Comparing two different architectures needs a distinction between steps that touched the world and steps that were internal bookkeeping. The plan-execute system records an interpret_request decision that the ReAct system has no analogue for; the guarded system records blocked: entries for actions it refused. Counting those made two systems that did exactly the same things look 0% alike. Equivalence therefore compares effect paths: tool calls only.

Chapter 30Typed argument comparison

This is the technical contribution, and it is the thing the closest paper listed as future work.

Comparing tool arguments with a single equality operator produces both false alarms and misses. "INV-1029" versus "inv-1029 " is not a divergence. amount=49.0 versus amount=490.0 is the most expensive divergence in the system. One operator cannot tell those apart, so comparison is typed per field.

PolicyApplies toRule
EXACTidentifiers, account codes, enum-like valuesNormalise whitespace and case, then demand equality. Any difference is a different referent.
NUMERICmoney, quantities, thresholdsExplicit absolute and relative tolerance, defaulting to zero. On a payment instruction, "close enough" is the defect.
TEXTfree-text reasons and notesNormalised and compared, but at low severity, because rewording a note is not the same class of defect as changing an amount.
IGNOREtimestamps, request ids, idempotency keysLegitimately allowed to vary. Declaring these explicitly is what keeps the signal clean.
SETcollections whose order carries no meaningCompare as sets.

Unclassified fields fall back to a deliberate bias: numbers get zero-tolerance numeric, everything else gets exact. An unclassified field that changes should surface and be triaged, not silently forgiven.

The comparison that only works against ground truth

Argument checks compare against the task's true value, not against other runs. This matters enormously. If every run pays $48,200 instead of $4,820, then comparing runs to each other shows perfect consistency. Only ground truth catches a systematic error. There is a test for exactly this case: eight runs, identical paths, identical arguments, 100% consistency, 0% conformance.

Chapter 31Sequence alignment, and why naive comparison lies

Suppose the reference path is fetch → match → dup → pay and a run omits dup. Compare position by position and you get: at step 2, expected dup, got pay. That reads as a substitution, as though the agent swapped one check for another. It did not. It skipped a control, and everything after shifted up by one.

The distinction is not cosmetic. A skipped control is a policy violation. A substituted one is a routing error. They have different causes and different fixes.

The solution is Needleman-Wunsch global alignment, published in 1970 for comparing biological sequences and equally applicable here. It finds the alignment of two sequences that maximises a score, allowing gaps, and recovers the actual edit script: match, substitute, skipped, extra.

reference:  fetch  match  dup   pay
candidate:  fetch  match   —    pay
                          ^
                    SKIPPED, not substituted

Scoring is match +2, mismatch −1, gap −2, chosen so a single omission aligns as one gap rather than cascading every downstream step into a mismatch. There is a test asserting exactly that: one skipped step must produce one divergence, not three.

Chapter 32The invariant DSL

A consistency score is a description. "78.5" tells an engineer nothing to act on and a compliance reviewer nothing to sign. An invariant is a claim that is either upheld or broken, and when it breaks it breaks at a specific step for a specific reason.

MustCall("check_duplicate")
Ordering("match_purchase_order", then="schedule_payment")
CallAtMost("schedule_payment", 1)
ArgEquals("schedule_payment", "amount", from_context="expected_amount")
MustNotCall("schedule_payment", when=lambda ctx: not ctx["should_pay"])
ArgSatisfies("request_approval", approval_route_ok)

Each carries a declared severity: critical, high, medium, low. Severity is declared rather than inferred, because the tool cannot know that schedule_payment is denominated in money and post_audit_log is not. Every aggregate is reported both overall and restricted to critical, since averaging a missing log entry together with a duplicate payment produces a number that means nothing.

Invariants can be conditional. MustCall("request_approval", when=needs_approval) only applies to invoices over the threshold. Without conditionality the approval-ordering rule fired on every small invoice, which was a false positive found and fixed early.

All invariants are effect-based: a call that raised did not happen, so it cannot satisfy a MustCall, cannot license a subsequent step under Ordering, and does not count toward CallAtMost. A failed payment attempt that was later retried is one payment, not two.

Chapter 33The perturbation engine

Six perturbations, each declaring the invariant it preserves.

NameWhat it changesWhat must not change
baselinenothing; the identical request repeatedeverything. This measures raw self-consistency and separates sampling noise from brittleness.
paraphrasethe request is reworded by a model, then verified by a second independent model callwhich steps are correct
distractorunrelated office chatter added before and afterwhat is done
tool_faultone tool call fails once with a 503, rate limit or connection reset, then recoversthe outcome
decoy_toolsplausible but irrelevant tools added to the available setwhich steps run
samplingthe identical request at a raised temperaturewhich steps are correct

Keeping baseline in the suite rather than treating it as a control is deliberate: its number is diagnostic on its own. An agent whose baseline self-agreement is 80% is not brittle under perturbation, it is brittle full stop, and no amount of work on the perturbed variants will fix that.

Faults are injected at the toolbox boundary through a hook called before every tool body, so neither the agent nor the tool implementation knows. The agent sees a real error from a real call.

Chapter 34The runner, the cache, and the budget

Variants are generated once per task and shared across all arms. That is what makes the arms comparable: every system sees the identical reworded requests, the identical injected faults, the identical decoy tools. Each trial gets its own toolbox and therefore its own database, so trials cannot contaminate one another and can run in any order.

A cache subtlety that would have faked the entire result

Caching model responses saves money. But a cache keyed only on the request destroys the measurement. Self-consistency is measured by issuing the same request several times and seeing whether the agent does the same thing. Serve those from one cached response and self-consistency comes back a perfect 100% every time, as an artifact of the cache rather than a property of the agent.

So the cache key includes the trial identity. Replaying trial 3 replays trial 3's recorded calls exactly, which makes a published result reproducible. Running a new trial 4 goes to the API and samples afresh. You get replayability without manufacturing agreement.

The budget is a hard spend cap, journalled to disk after every call so that a process killed mid-run cannot take its spend record with it, and loaded on startup so the cap bounds total spend across runs rather than per run. Both of those properties exist because their absence cost real money; Chapter 40 has the story.

Chapter 35Three different questions

The analysis layer answers three questions that are easy to conflate and must not be.

AnalysisQuestionCatches
ConformanceDid this agent obey its own declared rules?An agent that is consistently wrong. Every run identical, every run violating a control.
ConsistencyDoes this agent behave the same when the input is reworded?An agent that is erratically right. This is the state that passes evals and fails in production.
EquivalenceDoes the replacement do what the incumbent did?A migration that looks safe because outcomes match while behaviour has silently changed.

Neither of the first two subsumes the other, which is why both exist. The third answers a different question entirely and is the one that gates retiring a legacy system.

Why equivalence is the stronger foundation

Conformance and consistency only report something when the agent fails. Against a competent model you can measure nothing, which is exactly what happened in the first study: every arm hit 100% outcome correctness and the only effect found was 3.7% on one perturbation.

Equivalence reports something whenever two systems differ, and two systems always differ somewhere. Its output does not depend on either side being bad. That is a structurally better thing to build on.

Chapter 36The certificate

The headline number is deliberately not the observed average. It is the 95% lower confidence bound on critical-invariant conformance under the worst perturbation. Three reasons, each of which comes up the moment someone challenges it:

  • Worst case, because averaging is how a dangerous perturbation gets buried. An agent that holds at 99% everywhere except paraphrase, where it pays blocked invoices, is not a 96% agent.
  • Critical only, because a missing audit-log entry and a duplicate payment are not commensurable.
  • Lower bound, because a certificate should state what you can defend, not what you saw on a good day. This also makes small studies self-penalising, which is correct.

The certificate carries its own provenance: model, seed, perturbation suite, policy identity, cost, git commit, and a hash of the trajectory evidence. And plumbline certify rebuilds it from stored traces with no model calls. Hand somebody the trajectories file and they can reconstruct the number themselves. A certificate you cannot re-derive is an assertion, not evidence.

The parity certificate has its own verdict logic, and it distinguishes three states rather than two. Twelve runs with zero divergences is not evidence of equivalence and is also not evidence of divergence. Reporting "materially different" there would send someone to debug a system that is fine. So it says the sample is too small and states how many more clean runs a 0.95 bound needs.

Part VIII · The experiment

Chapter 37Design

One question: when you move an agent's control flow out of the model, what do you actually buy, and where does the remaining risk go?

Held fixed: the eight invoices, the eight tools, the sqlite database, the model (Claude Haiku 4.5), the perturbation variants (generated once and shared), and the declared policy. Changed: who decides which step runs next.

738 runs completed. Two arms, eight tasks, six perturbations, four variants each, two trials. $11.02 total spend. The run stopped at 738 of a planned 768 because the cumulative spend cap fired, which is the safety mechanism working rather than a failure.

Stating a weakness before anyone else does

The plan-execute arm's structural conformance holds by construction: the executor runs every check because there is no branch in which it does not. That is not a trick and it is not hidden. It is the point. Putting control flow in the runtime converts a probabilistic guarantee into a structural one. What the study measures is where the residual risk goes, and it refuses to assume the answer.

The result I published

Reading only the first and third columns: under an injected transient tool failure the deterministic executor reached the correct outcome 81.2% of the time against the agent's 98.2%. +17.0 points, p = 0.0025. The control comparison, on every condition except tool faults, gave p = 0.48, not significant. The effect was localised to one condition with everything else flat, which is precisely the signature of a real effect.

It went into a report, a chart and a draft post. The headline was that determinism makes agents more brittle, not less.

The result that survived

The retraction

My deterministic executor treated any tool error as a blocking condition. It had no retry policy. No production finance system behaves that way: every RPA platform has retry, every payments integration has backoff, and a single 503 on a routine check is the normal weather of a network rather than a reason to halt.

I noticed this, wrote it down as a limitation, and published the headline anyway. Somebody who had actually shipped a payments integration read the setup and said so plainly.

Adding a retry policy and re-running the identical 768 trials closed the gap completely:

naive → retry :  +18.8 pts   p = 0.0005   significant
retry → react :   −1.8 pts   p = 0.4620   NOT significant

Three lines of retry logic. A well-built deterministic executor is statistically indistinguishable from a free-form agent on this task. The 17-point effect was measuring my missing error handling and nothing else.

Chapter 39What it means, and what it does not

The honest finding is not about determinism at all. It is about how agent benchmarks are constructed, and it is more useful than the result it replaced.

The finding, stated properly

Everything downstream of the baseline was correct. The confidence intervals were correct. The permutation test was correct. The control condition was correct and behaved exactly as a control should, showing the effect confined to one perturbation while everything else stayed flat.

The result was still an artifact, and no amount of statistical rigour would have caught it, because the flaw sat upstream of the statistics. Only domain knowledge finds a bad baseline.

Every agent benchmark has a baseline somebody chose. When you read one, the question that decides whether the number means anything is not which statistical test was used. It is whether the thing being compared against is a system anyone would actually deploy.

What the study genuinely established

  • Nothing broke either architecture under paraphrasing, distractor text, decoy tools or sampling variation. The failure mode the literature emphasises did not appear at all on this task with this model.
  • A well-built deterministic executor and a free-form agent were indistinguishable (p = 0.46). Determinism did not buy measurable reliability here. It also did not cost any.
  • Determinism buys predictability, not reliability. The deterministic system does exactly what its author specified. When the specification is complete, it is perfect and auditable. When it is not, there is no fallback, which is what the naive arm demonstrates in miniature.
Why there is no dramatic result

A task with unambiguous ground truth and independent boolean checks leaves a competent model no room to fail. Every condition sat at 100% except the one my own bug created. The domain, not the model, is why the study measured so little.

That is the reason the repository now carries a much richer AP domain: twenty invoices across thirteen exception classes, category-dependent tolerances where the same variance passes on one line and fails on another, and fuzzy duplicate detection that returns a confidence rather than a boolean. Failure lives in ambiguity, and the first domain had none. That domain has not yet been run against a live model.

Limits

One model (claude-haiku-4-5), one domain, one policy. Perturbations are a chosen finite set: passing them is evidence, not proof. And as this chapter shows, so is the choice of what to compare against.

Part IX · Epistemics, or: every bug and what it taught

Chapter 40The bugs

This chapter is the most useful part of the project to have lived through. Ten defects, and the pattern across them matters more than any one of them.

Every single one produced plausible output. None raised at the top level. A tautology with a certificate printed on it. A spend cap reporting zero. A clean bill of health on a control that errored. A crash that looked like behavioural collapse. A billing artifact that looked like a result. A cost figure understated sixfold. A baseline nobody would deploy, producing a significant effect.

That is precisely the failure mode this project exists to detect, committed repeatedly by its author. Not one was caught by the 80 tests. Almost all were caught by a person looking at actual output and asking whether it made sense.

1. The circular experiment

The first version simulated the agent. A step was either "stochastic", failing with a hardcoded probability, or "pinned", always firing correctly. The demo pinned a step and showed reliability rise.

That proves nothing. It proves a step defined as always-correct is always correct: a tautology with a certificate on top. Discarded entirely. Lesson: if your experiment cannot come back negative, it is not an experiment.

2. The budget cap that failed open

The environment file specified a dated model id absent from the price table. PRICES.get(model, (0.0, 0.0)) returned zero, so every call recorded $0.00 and the hard spend cap could never fire. Lesson: a safety mechanism that fails silently is worse than none, because you trust it.

3. The harness certified a control that never ran

On the first live run, an agent called check_vendor_status with the vendor name instead of the id, got an error, never retried, and the certificate reported no violations. MustCall counted the failed attempt as the control having executed. Lesson: a measuring instrument that reports a control as satisfied when it errored is actively dangerous. All invariants became effect-based.

4. Crashes reported as findings

Every sampling-perturbation run threw TypeError: unexpected keyword argument 'temperature', because the SDK had removed sampling parameters. The crashed runs had empty trajectories, which the analyser correctly read as "no steps ran" and reported as every step skipped, including the first.

That looks like a dramatic finding. "Temperature causes total behavioural collapse" would have gone straight into a post and been trivially falsifiable. Lesson: an error path and a finding can be indistinguishable in aggregate. Read the trajectories.

5. The billing artifact that inverted the headline

The first full study's summary said free-form agents beat deterministic ones. The actual cause: API credits ran out at run 494. The runner processes arms in order, so later arms lost runs to empty trajectories, which scored as total violation. Lesson: check the error column before reading the result column.

6. Under-reporting the cost sixfold

Reported spend was $0.69; the real figure was $5.53. Three compounding causes: the cap was per-process so five runs meant five ceilings; a study killed at a timeout took its spend record with it; and the rerun hit a warm cache, paid for 21% of calls, and reported that as the study's cost.

Lesson, and the sharpest one: this project's premise is that you cannot trust a number until you look behind it, and its author quoted a cost figure he had not looked behind. The user caught it, not the code.

7. A test that corrupted the thing it tested

The regression test for the spend cap journalled a fake $6.00 into the real ledger, inflating the live cap from $5.53 to $11.53. There is now a guard test that fails if any test constructs a budget without an isolated ledger.

8. A wrong diagnosis, recorded as wrong

Prompt caching never engaged across 1,962 calls. The hypothesis was that the prefix sat under the documented ~1024-token minimum. The system prompt was expanded to clear it. Caching still did not engage, at 1,878 tokens or at 3,078, with the directive passed two different ways.

Length was never the cause. The code comments said it was, which would have sent the next person down the same dead end, so they now record what was measured and explicitly decline to assert a cause. Lesson: a confidently wrong comment is worse than no comment.

9. The strawman baseline

Covered in full in Chapter 38, and it belongs here because it is the same pattern rather than a different kind of mistake. The deterministic executor had no retry policy. The 17-point result it produced was significant, localised, correctly bounded, and entirely an artifact.

What makes it the worst of the ten is that I noticed. I wrote the limitation down, and then published a headline the limitation contradicted. Documenting a flaw is not the same as accounting for it.

10. Incomplete runs scored as violations

Fifty-two cut-off trials were counted as invariant failures, dragging a certified bound from 94% to 41%. An incomplete run is missing data, not evidence. The same artifact class as number 5, appearing again in a different part of the system months of work later.

What ten defects are evidence for

The instrument was correct throughout. The statistics were correct. The tests passed. And the output was wrong in six distinct ways, each time in a form that looked entirely reasonable.

This is not irony. It is the strongest available evidence that the problem the project describes is real: a system that produces confident, well-formed, plausible output is not thereby producing correct output, and the gap is invisible from the inside. That was true of an AI agent processing an invoice, and it was true of the harness built to measure it.

Instruments need instruments. And past a certain point they need a person who knows the domain to look at the setup and say that is not how anyone actually does this.

Part X · Explaining it

Chapter 41How to say this to different people

In one sentence

"When an AI agent does a job for you, you can see what it produced but not what it did, and I built the instrument that measures the difference."

To a non-technical person, thirty seconds

"An invoice comes in and an AI is supposed to run four checks before paying it. I found cases where it skipped checks, got the right answer anyway through a different route, and wrote a confident summary that never mentioned the skipped steps. Every existing tool grades the answer, so every existing tool passes that run. In accounts payable, skipping a control is an audit finding whether or not the money was right."

To an engineer, two minutes

"You declare invariants your agent must never violate. The tool attacks them with metamorphic perturbations, input changes that must not alter correct behaviour, and reports which invariant broke, at which named step, with a confidence interval. Two things are new. It compares tool arguments against ground truth, not just which tools ran, which is what the closest paper listed as its own future work. And it does divergence localisation with Needleman-Wunsch, so a skipped control reports as a skip rather than a substitution of whatever followed it."

To someone who asks about the finding

"I measured a 17-point reliability gap between a deterministic executor and a free-form agent. Significant, p = 0.003, localised to one perturbation with a clean control. Then somebody pointed out my deterministic executor had no retry policy, which no production system lacks. I added one, re-ran the identical 768 trials, and the gap vanished completely: the two became statistically indistinguishable at p = 0.46.

So the finding is not about determinism. It is that a plausible, significant, correctly-bounded agent benchmark result can be entirely an artifact of the baseline, and no statistical rigour catches it, because the flaw is upstream of the statistics. Only domain knowledge does. Every benchmark you read has a baseline somebody chose."

Chapter 42The hard questions, and honest answers

"Doesn't this already exist? Isn't this what Patronus does?"

"Tools exist and they're well funded, and I'm not claiming to compete with them. They do scenario generation and trace scoring on fixed inputs. This is a different axis: hold the scenario fixed and vary only the surface form. And I'm not offering a product, I'm offering a result. Nobody has published this measurement."

"You measured a small model on a toy task."

"Correct, and the report says so in the limits section. Haiku 4.5, one AP domain, eight invoices, one policy. The harness runs against any model you point it at. The claim is architectural, not a model ranking."

"Your deterministic arm was just badly written."

"Correct, and that is now the published result rather than a caveat on it. I retracted the original headline, kept the badly-written executor as a permanent control arm so the effect can be attributed rather than repeated, and the report leads with the retraction. The interesting question is not whether I got it wrong. It is that everything except the baseline was right, and that was not enough."

"How do I know your perturbations preserve meaning?"

"Every reworded request is verified by an independent model call that sees the original and the rewrite. Failures are discarded and counted, and the count appears in the report. The guard isn't infallible and its failure mode is asymmetric: likelier to wave through a subtle shift than reject a valid rewrite. It raises the floor, it doesn't guarantee."

"Why should I believe the numbers?"

"Every trajectory is stored. plumbline certify rebuilds the certificate from them with no model calls. Take the file and reconstruct the number yourself. And I'd point you at the bugs chapter, because most of them were headline numbers that turned out to be artifacts, and I found them by reading trajectories instead of trusting summaries."

"What would you do next?"

"Ingest a real UiPath .xaml so the incumbent side is an actual legacy bot rather than another arm of my own harness. That turns a demonstration into the thing enterprises need, because the equivalence proof is the step that gates every RPA migration and today it's done by running both systems side by side for thirty days and eyeballing it."
