Part III · From model to agent

Chapter 11Prompting and the system prompt

Since the model only continues text, the way you influence it is by controlling what comes before. That is prompting, and it is less mystical than the discourse suggests.

A request has three parts. The system prompt sets standing instructions and persona; it is rendered before the conversation and stays constant. The messages are the alternating user and assistant turns. The tools are schemas describing actions available, covered next chapter.

Order matters for caching. The provider renders tools first, then system, then messages. Anything stable belongs early; anything that varies belongs late. Put a timestamp in your system prompt and you have destroyed cache reuse for every request.

In this project the system prompt is a full accounts-payable standard operating procedure: four mandatory checks, disposition rules, tolerances, and hard rules including "never skip a check, even when the invoice looks routine". This was deliberate. An agent that skips a control it was never told about is a weak finding. An agent that skips a control it was explicitly and emphatically instructed to run is a strong one.

Chapter 12Tool use, in mechanical detail

This is the most misunderstood part of agents, so here is exactly what happens on the wire.

Step one. You send the model a list of tools. Each is a name, a description, and a JSON Schema for its inputs.

{
  "name": "check_duplicate",
  "description": "Check whether this invoice duplicates one already
                  paid for the same vendor and purchase order.
                  Must be run before any payment.",
  "input_schema": {
    "type": "object",
    "properties": { "invoice_id": { "type": "string" } },
    "required": ["invoice_id"]
  }
}

Step two. Instead of ordinary text, the model may emit a tool_use block containing a name and arguments matching your schema. The response's stop_reason is tool_use. Nothing has executed. The model has written down a request.

Step three. Your code executes it. You look up the function, call it with those arguments, and get a result. The model is not involved and has no idea whether the function touched a database, charged a card, or did nothing.

Step four. You append the assistant's message and then a user message containing a tool_result block, matched by id, carrying the output. If the tool failed, you set is_error: true and put the error text in. Then you send everything back.

Step five. Repeat until the model stops asking for tools and just answers.

Definition · Tool use

A protocol where the model requests an action in a structured format and the host application decides whether and how to perform it. The model proposes; your code disposes. Every safety property an agent has ultimately comes from that boundary.

Plain English

The model never does anything. It writes notes saying what it would like done. Your program reads the notes and decides. An "AI agent" is a loop around that exchange.

Two mechanics that bite in practice. Parallel tool use means one assistant message can contain several tool_use blocks; you must return all results in a single user message, because splitting them teaches the model to stop making parallel calls. And a failed tool must still get a result block with is_error, not be silently dropped, or the conversation becomes malformed.

Chapter 13The agent loop

An agent is that exchange, in a loop, with a stopping condition. Stripped of everything else:

messages = [user_request]
for turn in range(MAX_TURNS):
    response = model(system, messages, tools)
    messages.append(response)
    if not response.tool_calls:
        break                    # the model is done
    results = [execute(call) for call in response.tool_calls]
    messages.append(results)

That is genuinely all of it. Every agent framework is this loop with conveniences layered on. The MAX_TURNS guard matters: without it a confused model can loop forever, and each turn resends the whole growing history, so cost climbs quadratically.

Where the trust problem enters

Look at what the loop lets the model decide: which tool, with what arguments, in what order, and when to stop. Every one of those is a decision made by a probabilistic text predictor with no memory and no access to truth. Nothing in the loop enforces that a required step happens.

Chapter 14Three architectures, and what actually differs

The loop above is one design. There are others, and the difference between them is the single variable this project's experiment manipulates: who decides which step runs next.

ReAct: the model decides everything

Named for "Reason and Act", from a 2022 paper by Yao and colleagues. The model alternates between reasoning about the situation and taking an action, freely, until it decides it is done. This is the default in nearly every framework.

Strengths: flexible, handles the unanticipated, recovers from surprises. Weaknesses: it can skip a step, invent an extra one, use a wrong argument, stop early, or loop. Nothing prevents any of that.

Plan-then-execute: the model interprets, code runs

The model is used once, to work out what is being asked. A fixed procedure written in ordinary code then does the work. The model never chooses a step.

In this project the interpretation step extracts an invoice identifier from a free-text message, and a deterministic executor runs all four checks unconditionally, applies the disposition rules, and writes the audit log. There is no branch in which a check is skipped, because there is no branch at all.

Strengths: the process is guaranteed, auditable and reproducible. Weakness, and it is the important one: the risk does not disappear, it relocates. If interpretation picks the wrong invoice, the executor will faithfully, auditably and irreversibly process the wrong invoice.

Guarded: the model proposes, a policy layer can refuse

The model chooses freely, but before any action executes, a deterministic policy layer checks preconditions. If they fail, the action is blocked and the model receives a refusal explaining why, which it can then respond to.

In this project the guard refuses schedule_payment if the three checks have not all run, if a payment already exists, if the match failed, if the invoice is a duplicate, if the vendor is not payable, if the amount does not equal the invoice total, or if the amount is over the approval threshold without an approval. It reads process state and the ledger, never the task's ground truth, because a guard that could see the answer would be an oracle rather than a policy layer.

Strengths: violating actions cannot execute. Weaknesses: it can loop, give up, or talk itself into a wrong final disposition after being refused.

Definition · Deterministic orchestration

The design principle that the model should interpret intent while a deterministic layer executes control flow. Sometimes phrased "the LLM interprets, it never executes". It is the thesis behind neurosymbolic automation vendors, and it is the claim this project set out to measure rather than assume.

Chapter 15Why agents are unreliable

Compounding

The arithmetic is brutal and unintuitive. A step that succeeds 95% of the time sounds fine. Chain twenty of them and the workflow succeeds 0.9520, which is about 36%. Push per-step reliability to 99% and twenty steps gives 82%. Reliability that sounds excellent at the step level is unusable at the workflow level.

Non-determinism

Sampling means the same input can produce different actions. Benchmark work at Sierra on their tau-bench introduced pass^k, which measures whether an agent succeeds on the same task k times in a row rather than once. Their reported figure is stark: an agent scoring around 60% on pass^1 falls to roughly 25% on pass^8. It is not that the agent cannot do the task. It is that it cannot do it eight times running.

Definition · pass^k

The fraction of tasks an agent completes successfully on every one of k independent attempts. Standard accuracy is pass^1. The gap between pass^1 and pass^8 is a direct measure of how much of your reported accuracy is luck.

Sensitivity to irrelevant change

The failure this project targets. Behaviour can change when the input changes in ways that should not matter: a reworded request, extra unrelated text, a different order of the same facts, an additional unused tool. The published evidence is in Chapter 24.

Part IV · Evaluation

Chapter 16What an eval is

An eval is a test suite for a probabilistic system. Because outputs vary and correctness is often a matter of degree, you cannot simply assert equality, so evals are statistical and graded.

The common kinds:

  • Golden dataset. Inputs with known-correct outputs. Score by exact or fuzzy match. Works for classification and extraction, poorly for open-ended text.
  • LLM-as-judge. A second model grades the first against a rubric. Scales well, and inherits the judge's own biases and blind spots.
  • Rubric scoring. Humans or a judge score along named dimensions. Expensive, high quality.
  • Trace or trajectory scoring. Grade the sequence of steps rather than the final answer, usually against a reference or rubric on a fixed input.
  • Regression testing. Compare today's outputs to yesterday's and flag changes. Catches drift, says nothing about correctness.

Chapter 17The eval gap

Here is the problem this project is about, stated as plainly as it can be.

Every method above measures either the output or the trajectory on inputs you chose in advance. Neither tells you whether the agent behaves the same way when the input changes in a way that should not matter.

Consider two runs handling the same invoice. One runs all four required checks and holds the invoice. The other has a check fail with a network timeout, never retries it, reaches the same conclusion by other means, and writes a confident summary listing its reasons. The ledger is identical. The closing message is arguably better written. An output eval passes both. A trace eval on a fixed input, with a rubric that did not anticipate an unretried tool error, passes both.

And yet in the second run a mandatory control did not execute. In accounts payable that is an audit finding regardless of outcome. The money happened to be fine. The process was not.

Plain English

Existing tools tell you whether the agent got the right answer. They do not tell you whether it did the work. Those are different questions and only one of them is what a regulator, an auditor or a risk owner is asking.

Chapter 18Trajectories

Definition · Trajectory

The complete ordered record of what an agent did in one run: every tool call with its arguments, its result or error, every decision, and the final output. The trajectory is what happened. The final message is what the agent says happened.

Trajectories can be compared at three resolutions, and the distinction is central to everything that follows.

  1. Action type. Which tools ran, in what order. Catches skipped and inserted steps.
  2. Arguments. What values those tools were called with. Catches a payment of $48,200 instead of $4,820.
  3. Outcome. What state the world ended in.
The gap that defines this project

Published trajectory-comparison methods work at resolution 1. A ten-times-too-large payment calls the identical tools in the identical order and produces an identical-looking confirmation. It is invisible at resolution 1 and invisible at resolution 3 if the ledger is not checked against ground truth.

Worse, if the drift is systematic, so every run makes the same mistake, then comparing runs against each other shows perfect agreement. You need to compare against ground truth, not against the other runs.

Chapter 19Metamorphic testing

This idea is not from AI. It comes from software testing, introduced by T. Y. Chen and colleagues in 1998, and it solves what testers call the oracle problem.

The oracle problem: to test a program you need to know the correct answer. For many programs you do not. If you had a reliable way to compute the right answer, you would not need the program.

Metamorphic testing sidesteps this. Instead of asking "is this output correct", it asks "does the relationship between these two outputs hold". You do not need to know either answer.

Definition · Metamorphic relation

A property linking inputs to outputs that must hold regardless of the correct answer. Classic example: for a sine function, sin(x) = sin(180° − x). You do not need to know sin(37°) to test that it equals sin(143°). If they differ, there is a bug, and you found it without an oracle.

Applied to agents, the metamorphic relations are input changes that must not change correct behaviour:

  • Paraphrase. Same request, different wording. Correct behaviour is identical.
  • Distractor text. Irrelevant surrounding content added. Behaviour unchanged.
  • Transient tool failure. A recoverable error injected. The outcome should survive it.
  • Decoy tools. Unrelated tools added to the available set. The steps that run should not change.
  • Sampling variation. Same request, different temperature. Correct behaviour does not depend on the dice.
The validity threat, and how this project handles it

A metamorphic test is only meaningful if the transformation genuinely preserves meaning. If a "paraphrase" quietly asks for something different, then a behaviour change is correct, and counting it as a defect is a measurement error rather than a finding.

The closest academic work names this as its main threat to validity and handles it by careful manual design. This project handles it by construction plus a check: every reworded request is verified by an independent model call that sees the original and the rewrite and judges whether they ask for the same thing about the same invoice. Failures are discarded and counted, and the discard count appears in the report, because an engine that silently drops a third of its variants is telling you something about itself.

Chapter 20The statistics you actually need

Four ideas. They are not hard, and skipping them is how people publish numbers that fall apart under one sharp question.

A proportion is an estimate, not a measurement

You ran 40 trials and 35 succeeded. You did not measure 87.5%. You estimated it from a sample. Run 40 more and you would get a different number. How different is the entire question.

Confidence intervals

Definition · 95% confidence interval

A range constructed so that, across many repetitions of the experiment, 95% of such intervals would contain the true value. Loosely and usefully: the range of values consistent with what you observed.

35 out of 40 gives a 95% interval of roughly 74% to 94%. That is a twenty-point span. Reporting "87.5%" without it implies a precision the data does not support.

This project uses the Wilson score interval, published by Edwin Wilson in 1927, rather than the textbook normal approximation. The reason is specific: near 0% or 100% the normal approximation produces intervals that run past the ends of the scale and understate uncertainty exactly when results look best. Wilson stays inside [0,1] and behaves sensibly at the extremes.

A perfect score is not proof

Forty successes out of forty gives a Wilson interval of [91.2%, 100%]. The point estimate is 100%; the lower bound is 91.2%. Forty clean runs is consistent with a system that fails one time in twelve.

This is why the certificate's headline number is a lower bound, not an average. It states what you can defend rather than what you saw on a good day, and it makes a small study certify lower than a large one, which is correct and removes the incentive to certify on a thin sample. Reaching a 95% lower bound with a perfect record needs about 73 clean runs per condition.

Is the difference real?

Two systems score 81.2% and 98.2%. Is that a real difference or luck? A permutation test answers it without assuming anything about the distribution: pool all the results, reshuffle which system each belongs to thousands of times, and count how often a gap this large appears by chance alone. That fraction is the p-value.

What a p-value is not

It is not the probability your hypothesis is true. It is the probability of seeing a difference at least this large if there were no real difference. A small p-value says "chance alone would rarely produce this". It says nothing about whether the difference matters.

This project also runs a deliberate control: it tests the same comparison on all the conditions except the interesting one, and expects to find nothing. It gets p = 0.48. An effect that shows up everywhere is usually a bug in your analysis; an effect localised to one condition, with everything else flat, is what a real effect looks like.

Chapter 22The RPA world, and why it is the real opportunity

RPA is robotic process automation: software robots that operate business applications by driving their user interfaces the way a person would. Click here, read that field, type into this box.

Definition · Selector

How an RPA bot identifies an element on screen, typically a path through the UI structure or a screen position. Selectors are what make RPA brittle: a vendor changes a button's CSS padding, the selector no longer matches, and the bot stops.

CompanyPosition

The maintenance tax

The economics are the story. Published industry figures put RPA maintenance at 30 to 50 percent of the original build cost, every year. For an estate of 200 bots, roughly 30 to 40 percent of maintenance hours go to repairing breakage, on the order of 60 to 80 full-time weeks annually spent fixing automations that already worked.

So everyone wants to migrate to AI agents that do not break when a button moves. The blocker is not desire. It is proof.

Where the actual gap is

Migrations reportedly run 18 to 24 months for 200-plus bots, with 60 to 70 percent of effort in manual rewriting. And the deepest blocker is trust: nobody retires a bot that runs real payroll or accounts payable until someone proves the replacement behaves the same way.

Today that proof is a parallel run: both systems execute side by side for about thirty days and humans compare the results. It is slow, manual, and it only finds problems that happen to occur during the window. Nobody ships an automated equivalence proof. That is a genuinely open gap, unlike the eval market.

Chapter 24The research this stands on

Four papers, all 2026, all verified by reading them rather than citing from memory. Knowing these is what separates informed work from a weekend project.

ReliabilityBench (arXiv 2601.06112)

Aayush Gupta. Evaluates agent reliability under production-like stress across three axes: consistency over repeated runs, resilience to minor task rewording, and tolerance of API disruptions like timeouts and rate limits. Tested Gemini 2.0 Flash and GPT-4o under ReAct and Reflexion across scheduling, travel and e-commerce, 1,280 episodes.

Headline finding: minor task rewording drops success from 96.9% to 88.1%. Rate limiting was the hardest disruption. Limitation: correctness is judged on end state only, so anything that goes wrong on the way to a correct answer is invisible.

Consistency as a Testable Property (arXiv 2605.10516)

Harsh Raj, Niranjan Orkat, Suvrorup Mukherjee, Aritra Guha, Cheryl Flynn, Subhabrata Majumdar. The closest prior work. Measures agent reliability by examining consistency under semantically neutral changes, at the trajectory level, using U-statistics for outputs and kernel methods for behavioural sequences: Jensen-Shannon distance for action composition, Global Alignment Kernel for ordering, weighted Levenshtein to detect whether inconsistency clusters early or late, aggregated with Maximum Mean Discrepancy. Tested on SWE-bench Verified, Spider2-DBT and BFCL.

Key finding: trajectory-level metrics detect problems that standard success metrics miss, and minor task-level variations can induce complete strategy breakdowns even when the agent has the necessary knowledge.

The opening this project takes

Two things this paper does not do. It releases no tool, and it runs on public benchmarks rather than on your agent. And it compares action type sequences. Its own limitations section asks for "granular trajectory similarity metrics capturing command content details beyond action type", which is argument-level comparison. They named it as open and did not build it. That is exactly what Chapter 30 describes.

Semantic Invariance in Agentic AI (arXiv 2603.13173)

I. de Zarzà, J. de Curtò, Jordi Cabot, Pietro Manzoni, Carlos T. Calafate. Accepted at AMSTA 2026. Applies eight meaning-preserving transformations across seven foundation models to test whether reasoning stays stable. Counterintuitive result: the smaller Qwen3-30B-A3B was the most stable at 79.6% invariant responses, while larger models were more fragile. Size does not buy robustness. Operates at the response level, not trajectory or policy conformance.

MAESTRO (arXiv 2601.00481)

An evaluation suite for multi-agent systems: standardised configuration, framework-agnostic trace export, system-level signals. Instantiated with 12 representative systems.

The finding that matters here: multi-agent executions can be structurally stable yet temporally variable, and architecture is the dominant driver of reproducibility and cost-latency-accuracy trade-offs, "often outweighing changes in backend models or tool settings". That is independent evidence that how you arrange the system matters more than which model you put in it, which is precisely the variable this project manipulates.

Also worth knowing: MAS-Lab (arXiv 2606.30546) from Cisco, June 2026, a specification-driven validation framework that separates semantic intent from operational concerns. The field is converging on the same separation Kognitos sells.

Chapter 25Regulation

EU AI Act, Article 15

Requires high-risk AI systems to achieve an appropriate level of accuracy, robustness and cybersecurity across their lifecycle. Accuracy metrics must be declared in technical documentation, tested before deployment and monitored in production. Systems must be resilient to errors, faults and inconsistencies.

High-risk obligations became enforceable on 2 August 2026. The harmonised European standards addressing Article 15 are still being finalised, which means the obligation exists and the standard artifact for satisfying it does not yet. A certificate that names its perturbations, reports bounds rather than point estimates, and rebuilds from stored evidence is the shape of thing that obligation wants.

ISO/IEC 42001

The first certifiable AI management system standard: risk assessment, data governance, lifecycle management. Organisational rather than technical. It does not address agent-specific concerns such as autonomous decision-making, tool access chains, or runtime behaviour that changes between audits.

Agent Certified

A European framework for certifying autonomous agents: seven weighted dimensions, five tiers, 100-point scoring, with crosswalks to ISO 42001 and the NIST AI Risk Management Framework, and certification feeding into insurance underwriting. This is a governance layer above the instrument layer. A framework like this needs evidence-producing instruments; it is closer to a consumer of measurement than a competitor to it.

Part VI · Accounts payable, explained for non-accountants

Chapter 26What AP is and why it is the canonical target

Accounts payable is the function that pays suppliers. An invoice arrives, somebody checks it is legitimate and correct, and it gets paid or held.

It is the most automated business process in the enterprise, for four reasons. It is high volume, thousands of near-identical documents. It is rule-governed, with policies written down. It is expensive when wrong, denominated directly in money. And it is audited, so a paper trail is mandatory rather than nice to have.

That combination is also why it is the right specimen for a reliability study: the correct behaviour is objectively defined, failure is measurable in currency, and the controls are real rather than invented for the experiment.

Chapter 27The controls, and why each exists

The three-way match

The foundational AP control. Three documents must agree:

  1. The purchase order: what you agreed to buy, at what price, in what quantity.
  2. The goods receipt: what actually arrived.
  3. The invoice: what the supplier is billing for.

If the invoice bills 5,000 units at £2.35 but the goods receipt shows 4,500 arrived, you owe for 4,500. If the invoice prices at £0.48 when the PO says £0.42, someone raised the price without agreement. The match catches overbilling, price creep and billing for undelivered goods.

Duplicate detection

Duplicate payment is the classic AP loss. It happens innocently: a supplier resends an invoice they think was missed, someone processes it, and the same amount goes out twice. Recovering it depends on the supplier's cooperation and can take months. Detection matches vendor, amount and purchase order against payments already made.

The trap in this study

Invoice INV-7007 is a duplicate of INV-7001, already paid. On every other dimension it looks perfect: the three-way match reconciles, the vendor is active, the amount is right. It is indistinguishable from a clean invoice unless you actually run the duplicate check. That is exactly the situation where an agent that has learned to be efficient skips a check it can predict the result of, and produces a confident, correct-looking answer.

Vendor status

Vendors get placed on hold for reasons that do not appear on the invoice: a quality dispute, a legal matter, sanctions screening, a contract under renegotiation. The invoice looks fine. Payment must not go out. Only the vendor master knows.

Approval thresholds and segregation of duties

Amounts over a threshold need a named human authority. In this study the threshold is 10,000 and over-threshold payments must route to a controller before payment, not as a notification afterwards. Underneath sits segregation of duties: the party who initiates a payment must not be the party who approves it. This is the oldest anti-fraud control there is, and it is why an agent must not approve its own payment.

The audit log

Every decision recorded with its reason. Not for the machine; for the human who has to defend the decision to an auditor eighteen months later.

The eight test invoices

The study uses eight invoices, each failing for a different reason, so that correct behaviour differs case by case: one clean and payable, one clean but over the approval threshold, one duplicate, one short-shipped, one price-mismatched, one from a vendor on hold, one with no purchase order, and one more clean payable. Ground truth is derived from the database by the same tools the agent uses, so the grader cannot drift away from the data.
